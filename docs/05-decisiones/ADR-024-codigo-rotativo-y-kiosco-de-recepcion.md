# ADR-024: Código rotativo en la app y kiosco de recepción

- Fecha: 2026-10-28
- Estado: propuesta inicial

## Contexto

El control de acceso tenía motor, bitácora y acceso manual, pero ningún camino para que el socio entrara por su cuenta: el diseño original hablaba de QR, huella, tarjeta RFID y torniquete, y la vista previa solo permitía simular una lectura con `POST /preview/access/check`. Recepción podía registrar una entrada manual, no validar una credencial.

La opción más barata para operar mañana mismo es un **código numérico que la app del socio muestra y recepción captura en una tablet**. No exige hardware nuevo, funciona con la cámara o el teclado de una tablet común y reutiliza el motor de acceso existente. La alternativa (QR en pantalla + lector) requiere una cámara dedicada y una integración que el club todavía no tiene; la biometría y la tarjeta quedan para cuando exista el controlador físico (ADR-004).

El riesgo principal de un código es que se comparta: un socio podría enviar una captura a alguien más. Por eso el código debe caducar rápido, usarse una sola vez y emitirse con límites; y el dispositivo que lo valida debe estar autorizado, porque de lo contrario cualquiera con la URL del backend podría probar códigos.

## Decisión

- **Código de seis dígitos, cinco minutos, un solo uso.** `POST /member/access/code` (Bearer de socio, `201`) emite un código aleatorio de seis dígitos y responde `code`, `expires_at` y `expires_in_seconds`. El código vive cinco minutos, se guarda **solo como HMAC-SHA256** con `SECRET_KEY` (`member_access_codes.code_hash`) y no se puede recuperar después. Emitir uno nuevo marca como consumidos los códigos anteriores no usados del socio: solo hay un código vigente por socio, así que reabrir la pantalla no deja varios códigos válidos. El cupo es de **6 emisiones por socio cada 10 minutos**.
- **La emisión exige membresía vigente.** El servicio reutiliza la regla del portal: socio `active` y membresía `active` con `starts_at <= ahora < ends_at`; si no, responde `409` y no emite código. Un socio con membresía vencida no puede generar un código que luego sería rechazado en recepción.
- **Consumo atómico y decisión con el motor existente.** `POST /kiosk/check-in` recibe `{code}` y consume el código con un `UPDATE ... WHERE consumed_at IS NULL`; si el `rowcount` no es 1 (código inexistente, vencido o ya usado) responde `400` con «Código inválido o vencido.» y registra el intento. Cuando el consumo gana, arma un `AccessSnapshot` (estado y fechas de la membresía más reciente) y un `AccessRequest` de entrada con ocupación 0, llama a `evaluate_access` y escribe el resultado en `access_events` con `source = "reader"`, `reader_id = "Kiosco <etiqueta>"` y el nombre abreviado del socio (`Ana L.`). El kiosco **no reimplementa** reglas: si mañana el motor aprende horarios, adeudos o antipassback, el código los hereda.
- **El código es una credencial de entrada, no un pago.** El snapshot del kiosco no consulta adeudo, horario, límite diario ni antipassback: se envían como «sin restricción» y la ocupación como 0/1. Un socio con saldo pendiente entra (hoy el club no bloquea por adeudo en este canal) y el resultado solo depende de la membresía. Esto es una decisión de alcance consciente, no un olvido: el motor ya soporta esas reglas y conectarlas exige definir la política con el club. **Actualizado 2026-10-28:** el snapshot ya aplica el límite diario del plan (ADR-025) y la ventana de antipassback del club (ADR-026); el adeudo, el horario y el aforo siguen como «sin restricción».
- **Dispositivo autorizado con token propio.** El kiosco se registra desde el panel (`POST /admin/kiosk/devices`, permiso `settings.manage`, etiqueta de 1–80 caracteres) y recibe **una sola vez** un token `secrets.token_urlsafe(32)`; la base guarda solo su SHA-256 (`kiosk_devices.token_hash`, único) y el panel nunca lo vuelve a mostrar. Cada llamada a `/kiosk/check-in` lo envía en `X-Kiosk-Token`; un token desconocido o revocado responde `401` con `WWW-Authenticate: Kiosk`. Revocar (`POST /admin/kiosk/devices/{id}/revoke`) es inmediato: el mismo token deja de autenticar. `last_seen_at` se refresca como máximo una vez por minuto para no escribir en cada lectura.
- **Límites por dispositivo y bitácora de intentos.** Cada dispositivo admite **10 intentos por minuto**; al superarlo responde `429` («Demasiados intentos. Espera un momento.»). Los intentos inválidos se guardan en `kiosk_attempts` con el dispositivo, la hora y la clasificación (`invalid`), sin guardar el código capturado. Así un kiosco comprometido no puede probar códigos a velocidad de máquina, y la recepción puede ver que hubo intentos fallidos.
- **La membresía se evalúa otra vez al entrar.** La emisión exige vigencia, pero entre la emisión y la captura pueden pasar minutos. Si la membresía venció en ese lapso, el código se consume y el kiosco responde `200` con `authorized=false`, `reason="membership_expired"` y el mensaje «Membresía vencida. Pasa a recepción.»; no se reutiliza el código. El código solo prueba identidad, no congela el derecho de entrada.
- **La app muestra el código, no lo guarda.** `AccessCodeScreen` pide un código al abrirse, lo pinta agrupado (`397 969`), muestra la cuenta regresiva y un botón para generar otro cuando vence. La tarjeta «Acceso habilitado» del inicio ahora es un botón («Ver mi código →») y se deshabilita si `access_enabled` es falso. La pantalla no persiste el código ni lo deja en el historial de la app; el código vive en memoria hasta que se cierra.
- **El kiosco es una PWA estática y dependency-free.** `kiosk/` contiene `index.html`, `styles.css`, `app.js`, `manifest.webmanifest`, `sw.js` e `icon.svg`, servidos por cualquier servidor estático (`python -m http.server 8090 --directory kiosk`). La configuración (`apiUrl`, `token`, `label`) se guarda en `localStorage` y se valida con un ping a `/health` antes de guardar; si el backend responde `401` en un check-in, el token se borra y la pantalla vuelve a configuración con el mensaje de token revocado. El service worker cachea **solo el shell**: no hay validación offline ni cola de check-ins, porque un código de cinco minutos no tiene sentido sin red y el kiosco no debe decidir acceso con datos viejos.
- **El panel administra dispositivos, no códigos.** La página «Kiosco» (visible con `settings.manage`) lista etiqueta, estado, alta y última actividad, crea dispositivos, muestra el token una sola vez con botón de copiar y revoca con confirmación. El personal no puede ver ni emitir códigos de socios desde el panel: el código nace en la app del socio.
- **Actualización 2026-10-28 — la tablet también muestra la flota no disponible.** `GET /kiosk/equipment` usa el mismo `X-Kiosk-Token`, refresca `last_seen_at` igual que el check-in y devuelve nombre, ubicación, estado y etiqueta de los equipos en `maintenance`/`out_of_service`. La PWA los lista bajo el teclado («Equipos no disponibles hoy») y refresca al arrancar, al recuperar la red y cada minuto. Es un aviso de solo lectura: no participa en `evaluate_access`, no consume intentos y un `401` devuelve a configuración como el check-in.

## Consecuencias y límites

- El club ya puede operar la entrada con una tablet y la app, sin hardware adicional ni credenciales físicas. La bitácora existente registra cada entrada del kiosco con su lector, y el resumen del panel la cuenta como acceso del día.
- **El código se puede compartir.** Quien reciba una captura dentro de los cinco minutos puede entrar una vez. Mitigado por la vida corta, el uso único y el límite de intentos del kiosco; no hay segundo factor ni foto del socio en el kiosco. Antes de producción conviene decidir si recepción debe ver la foto o el nombre completo, y si un código usado por dos personas en poco tiempo debe alertar.
- **El token del kiosco es un bearer de larga vida.** Vive en `localStorage` de la tablet y no caduca hasta que se revoca; no hay rotación automática, fecha de expiración ni límite por IP. Cualquiera con acceso físico al navegador puede leerlo y validar códigos desde otro equipo. Mitigado porque el token solo permite validar códigos (no consultar socios ni cobrar) y porque revocar es inmediato; antes de producción hay que definir rotación, expiración y bloqueo del dispositivo.
  - **Actualización (2026-10-28, ADR-027):** el token ya caduca a los 90 días desde el alta o la rotación y se reemplaza desde el panel con `POST /admin/kiosk/devices/{id}/rotate-token` sin crear otro dispositivo; un token vencido responde el mismo `401` genérico que uno revocado. Siguen pendientes el límite por IP, el bloqueo por pantalla y el aprovisionamiento remoto.
- **Los límites son por dispositivo y por socio, no por IP ni globales.** Un atacante con varios tokens podría repartir intentos, y el código de seis dígitos tiene un millón de combinaciones: con 10 intentos/minuto por dispositivo la probabilidad por minuto es baja, pero el diseño no tiene captcha ni bloqueo de la cuenta del socio. El límite de emisión (6/10 min) acota cuántos códigos válidos existen.
- **No hay hardware.** El kiosco no abre torniquete, no lee QR ni RFID y no controla salidas. La entrada se registra como `direction="entry"`; no hay aforo en vivo porque el snapshot envía ocupación 0. La integración con el controlador físico sigue siendo deuda (ADR-004). Desde 2026-10-28 el kiosco sí aplica el antipassback del club (ADR-026) comparando la última entrada autorizada, y el límite diario del plan (ADR-025); lo que sigue sin existir es el control de salidas y el aforo en vivo.
- **No hay offline.** El service worker solo cachea el shell; sin red, la pantalla no valida. La cola offline del motor (`access_outbox`) no se usa desde el kiosco, y una entrada capturada sin red se pierde. El diseño offline del módulo sigue pendiente de transporte y hardware.
- **El kiosco no consulta adeudos, horarios ni límites.** Un socio moroso o fuera de horario entra si su membresía está activa. Es coherente con la operación actual, pero debe decidirse antes de presentarlo como control completo.
- **La app sigue mostrando el código después de usarlo.** La pantalla no sabe que el kiosco ya lo consumió; el contador sigue corriendo hasta el vencimiento. Es un detalle de UX: el código ya no sirve y generar otro lo reemplaza, pero la app podría avisar «usado» si el kiosco reportara el consumo (no lo hace).
- **El aviso de equipos del kiosco es un estado con retraso.** Se refresca cada minuto y no por push; si la consulta falla queda la última lista conocida, así que puede mostrar un equipo ya reparado o tardar en reflejar uno recién caído. No bloquea el check-in; el cartel de recepción (`kiosk/cartel.html`) muestra la misma consulta como pantalla pasiva con el token de un dispositivo propio.
- **No se registra el código capturado**, solo el intento inválido; un código válido queda como evento de acceso, no como intento. Tampoco hay auditoría de quién ve el token en el panel (solo `created_by` y `revoked_at`).
- **En vista previa el kiosco se sirve por HTTP y el token viaja en claro** en la red local; en producción exige HTTPS y una red de recepción de confianza. El CORS del backend debe incluir el origen del kiosco (`CORS_ORIGINS`), y el token no debe quedar en logs ni en capturas de soporte.
- **Sin pruebas en hardware real.** La verificación es en navegador de escritorio; falta probar en la tablet de recepción, con su teclado en pantalla, su brillo y su red.
